## 1. Зачем проект

Система-помощник: по извещению о закупке и приложениям находит места, где возможны нарушения
44-ФЗ, и подкрепляет каждое замечание дословными цитатами из документа и из нормы. Не замена
юристу и не юридическое заключение — черновик для проверки человеком.

Технические акценты MVP:

- документный RAG по корпусу 44-ФЗ с измеримым сравнением методов retrieval и чанкинга;
- обязательные цитаты с двух сторон и программная проверка groundedness;
- свой eval на решениях ФАС (включая отклонённые жалобы);
- on-prem инференс на CPU (llama.cpp) с замерами качества и скорости.

### 1.1. Не-цели (явно)

- Не юридический продукт и не замена экспертизе ФАС/юриста.
- Не бизнес-метрики («сократил время проверки на N%») — у MVP нет пользователей и процесса.
- Не мультиагентная система «ради агентов».
- Не аренда GPU: весь инференс локально на CPU.
- Не 223-ФЗ и не полный охват всех типов нарушений 44-ФЗ в MVP.

## 2. Постановка задачи

### 2.1. Вход

С 01.01.2022 (реформа 44-ФЗ, закон № 360-ФЗ) в электронных процедурах нет отдельной «документации о
закупке»: описание объекта закупки, требования и проект контракта — приложения к извещению (ст. 42).
Поэтому вход:

- извещение о закупке + приложения: описание объекта закупки (ООЗ / ТЗ), проект контракта;
- дата публикации извещения (для выбора редакции закона, см. §5).

Все данные — публичные, из ЕИС. **Перед стартом сверить детали реформы по тексту закона.**

### 2.2. Выход

Список **замечаний-кандидатов**. Каждое замечание — структурированный объект:

| Поле | Смысл |
| --- | --- |
| `doc_quote` | Дословная цитата из извещения / приложения |
| `doc_span` | Локатор в документе (файл + смещение / id фрагмента) |
| `norm_id` | Идентификатор нормы в корпусе (см. §4.2): статья / часть / пункт |
| `norm_quote` | Дословная цитата из текста нормы |
| `issue_type` | Тип из фиксированного enum (по темам, см. §3) |
| `verdict` | `violation` / `uncertain` / `insufficient_evidence` |
| `evidence_source` | Кто нашёл кандидата: эвристика / LLM |

Поле уверенности от LLM не используем: оно не откалибровано. Если нужна уверенность —
вычислять самому (согласованность нескольких прогонов, срабатывание эвристики + LLM).

**Инвариант:** замечание с вердиктом `violation` допускается только если:

1. `norm_id` существует в корпусе закона выбранной редакции;
2. `norm_quote` дословно (после нормализации пробелов, кавычек, дефисов) находится в тексте этой нормы;
3. `doc_quote` дословно (после той же нормализации) находится в исходном документе.

Иначе — `insufficient_evidence` или отбрасывание кандидата (политика фиксируется в eval).

### 2.3. Пользователи и режимы работы

Общая рамка для README — «помощник эксперту»: черновик мест для проверки человеком. Система **не**
выдаёт юридическое заключение.

Задача одна (найти нарушение с опорой на норму), но у двух пользователей разная цена ошибки — это две
рабочие точки на кривой precision / recall, а не две разные системы.

| | Режим «заказчик» | Режим «участник» |
| --- | --- | --- |
| Когда | До публикации извещения — самопроверка черновика | После публикации, до окончания подачи заявок |
| Цель | Найти и не допустить | Найти и обосновать жалобу |
| Цена пропуска | Жалоба, приостановка закупки, штраф | Упущенная возможность |
| Цена лишнего замечания | Минута на чтение (но при избытке инструмент перестают открывать) | Необоснованная жалоба, потерянное время |
| Приоритет | **Recall** при контроле precision | **Precision** |
| Что показываем | `violation` + `uncertain` | Только `violation` с полной двусторонней опорой |
| Вход | Пакет извещения + приложений (режим скана, §6.0) | Тот же скан **или** свой довод + фрагмент документа (режим довода, §6.0) |

Два **входа** в один пайплайн (не две системы):

1. **Режим скана** — пользователь загружает извещение и приложения целиком; система сама ищет
   кандидатов нарушений (эвристики; опционально LLM) и выдаёт список замечаний.
2. **Режим довода** — участник задаёт **отдельно** `complaint_argument` (текст довода / гипотезы) и
   `doc_fragment` (фрагмент извещения или приложения, к которому относится довод). UX: два поля
   (или явный формат ввода), не один неразмеченный текст. Дальше — один (или несколько после нарезки
   фрагмента) кандидат с запросом к retrieval из довода; эвристический поиск по всему пакету не обязателен.

Рабочая точка задаётся без LLM-confidence: фильтром по вердикту и правилом согласия источников
(например, для «участника» — кандидат найден и эвристикой, и подтверждён LLM). Кривая по голосованию
нескольких прогонов — после MVP: на CPU это дорого. После генерации — **не** сворачиваем ответы в один
вердикт «жаловаться / нет»: фильтр по `verdict` / режиму пользователя и **список замечаний** в JSON-отчёте
(лёгкое схлопывание дублей по одному месту/норме — по желанию, не блокер MVP).

## 3. Домен и сужение MVP

### 3.1. Корпус и темы

**Индекс — весь 44-ФЗ** на уровне пунктов. Иначе у retrieval нет конкуренции: при индексе только по ст. 33
почти любой метод даёт recall ≈ 100%, и сравнение методов ничего не показывает.

**Eval — по 3–4 темам** нарушений на этапе извещения:

| Тема | Нормы | Приоритет |
| --- | --- | --- |
| Описание объекта закупки | ст. 33, часто вместе с ч. 2 ст. 8 | MVP |
| Требования к участникам | ст. 31 | MVP |
| Содержание извещения | ст. 42 | После работающего пайплайна |
| Условия проекта контракта | ст. 34 | После работающего пайплайна |

Ст. 31 лексически близка к ст. 33 — retriever должен их различать. Ст. 42 и 34 добавляют другой язык и
другие части документа.

Позже: ст. 14 (национальный режим), ст. 23 + КТРУ, ст. 32 (критерии оценки — только конкурсы).

Исключаем из `gold_norms` процедурные нормы (ст. 105–106 и т. п.) — они есть почти в каждом решении и
загрязняют метрику.

### 3.2. Подзаконные акты

ФАС по описанию объекта закупки часто ссылается на правила использования КТРУ (ПП РФ № 145) и на
нацрежим (ПП РФ № 1875). **Решение для MVP:** в корпусе только 44-ФЗ; кейсы, где нарушение опирается
в основном на постановление, помечаются флагом `relies_on_bylaw` и исключаются из строгой метрики
retrieval. Включение ПП № 145 в корпус — первое расширение после MVP.

### 3.3. Объём данных MVP

| Артефакт | MVP | После MVP |
| --- | --- | --- |
| Eval-набор | **25–30** решений ФАС, ~6–8 на тему | 50–100 |
| Период решений / извещений | Извещения с **2025-01-01**; одна актуальная редакция 44-ФЗ | Более старая редакция + кейсы до 2025 |
| Отрицательные кейсы | Жалобы, признанные необоснованными, — с первого дня | Больше |
| Категории закупок | По возможности 1–2 однородных | Расширение |
| `issue_type` | 2–4 типа на тему, фиксируются после разметки первых кейсов | — |

Критерий пригодности кейса: из решения ФАС извлекается хотя бы один довод жалобы с вердиктом ФАС и
множеством норм, которые ФАС признала нарушенными (или констатация, что нарушения нет).

### 4.2. Корпус 44-ФЗ: что такое норма и схема после парсинга

Парсер закона выдаёт три слоя данных. Eval и валидаторы опираются на **NormUnit**; BM25 / dense — на
**Chunk**. Поисковый чанк нормой не является.

#### Что считаем нормой

**Норма** — структурная единица редакции 44-ФЗ, на которую можно сослаться так же, как ФАС: «ст. N»,
«ч. M ст. N», «п. K ч. M ст. N». У нормы есть канонический `norm_id` и дословный `text` в выбранной
редакции.

| Уровень | NormUnit в корпусе | В `gold_norms` | Примечание |
| --- | --- | --- | --- |
| Статья | да (узел дерева, заголовок) | если ФАС указала только статью | в индекс целиком обычно не кладётся |
| Часть | да | да | может быть одним чанком, если влезает в max |
| Пункт | да (**основной атом**) | да, основной случай | длинный пункт режется окнами, id пункта сохраняется |
| Подпункт | **нет отдельного id** | нет | текст подпунктов входит в `text` родительского пункта (**вариант B**) |
| Абзац / фраза / chunk | нет | нет | не адресуются без «абзаца после слова X» |

**Не норма:** фрагмент извещения, довод жалобы, поисковый chunk, пересказ своими словами, подзаконный акт
(ПП РФ и т. п. — см. §3.2, флаг `relies_on_bylaw`).

**Канон `norm_id`:**

```text
44FZ:{edition}:art.{N}[:ch.{M}[:p.{K}]]
```

Примеры: `44FZ:2024-07-01:art.33:ch.1:p.1`, `44FZ:2024-07-01:art.31:ch.2`.

`gold_norms[]` в eval и `norm_id` в замечании используют **тот же** канон. Recall по статье — проекция
`norm_id → article`; по части/пункту — точное совпадение id (без авторазворачивания «статья → все пункты»).

#### Слой 1: Edition (редакция закона)

Одна запись = один зафиксированный текст 44-ФЗ. В MVP редакция одна, но метаданные обязательны.

| Поле | Смысл |
| --- | --- |
| `law_id` | Код закона, напр. `44FZ` |
| `edition_id` | Код редакции, напр. `2024-07-01` — входит в `norm_id` |
| `effective_from` / `effective_to` | Период действия (`effective_to` = null для текущей) |
| `source_url` | Откуда скачан текст |
| `content_sha256` | Хеш `full_text` для воспроизводимости eval |
| `full_text` | Весь закон одной строкой в официальном порядке |

**Оффсеты** (`char_start`, `char_end`) у NormUnit и Chunk считаются в **символах Unicode** относительно
`Edition.full_text` (полуинтервал `[start, end)`, как в Python). После нормализации `full_text` текст
редакции больше не меняют — иначе все координаты съедут. Оффсеты нужны для: (1) скользящих окон внутри
длинного пункта; (2) проверки `norm_quote`; (3) связи Chunk ↔ NormUnit без хрупкого сравнения строк;
(4) двух режимов чанкинга из одного parse.

#### Слой 2: NormUnit (дерево закона)

Юридическая единица — источник правды для `get_norm_text(norm_id)` и валидаторов.

| Поле | Смысл |
| --- | --- |
| `norm_id` | Канонический id (см. выше) |
| `edition_id` | Ссылка на Edition |
| `article`, `part`, `point` | Компоненты адреса (`part` / `point` nullable) |
| `level` | `article` / `part` / `point` |
| `parent_norm_id` | Родитель в дереве |
| `title` | Заголовок статьи (у пунктов обычно пусто) |
| `text` | Дословный текст единицы (подпункты включены в текст пункта) |
| `char_start`, `char_end` | Позиция `text` в `Edition.full_text` |
| `order` | Порядок обхода закона |
| `is_retrieval_unit` | Можно ли взять вершину целиком как чанк (см. правила ниже) |

#### Слой 3: Chunk (поисковый индекс)

То, что индексирует BM25 / dense. Может быть короче NormUnit (окна).

| Поле | Смысл |
| --- | --- |
| `chunk_id` | Технический id чанка |
| `edition_id` | Редакция |
| `chunking` | `part` / `point` / `window` |
| `text` | Текст для поиска (заголовок статьи — отдельное поле или префикс; см. бенч §6.2) |
| `char_start`, `char_end` | Позиция в `Edition.full_text` |
| `norm_ids[]` | **Обязательно:** какие нормы покрывает чанк (для recall@k и hit по `gold_norms`) |

Hit в retrieval: пересечение `gold_norms` с объединением `norm_ids[]` у top-k чанков.

#### Правила чанкинга (структурный режим A)

Из одного parse строятся NormUnit и Chunk. Параметр **`max_chunk`** — предмет эксперимента;
**старт MVP: `max_chunk = 2000` символов** (по разметке корпуса 2026-08-04: ~92% частей
влезают целиком; окна нужны редко). Сравнивать также 1500 / 2500 на том же eval.

1. **Часть** целиком, если `len(text) ≤ max_chunk` → один Chunk, `chunking=part`,
   `norm_ids` = id части **и** всех пунктов внутри (hit и на уровне части, и пункта).
2. Иначе — по **пунктам** части.
3. **Пункт** целиком, если влезает → `chunking=point`, `norm_ids = [norm_id пункта]`.
4. Длинный пункт (или длинная часть без пунктов) → скользящие окна внутри него
   (`chunking=window`, overlap по умолчанию 200); у всех окон один и тот же `norm_ids`.

Режим B (окна фиксированной длины по всему закону) — отдельная генерация Chunk из тех же оффсетов; см. §6.2.

Заголовок статьи: в `NormUnit.title`; в `Chunk.text` опциональный префикс
`"{title}.\n{text}"` (флаг сборки) — сравнить на BM25 отдельно.

### 4.3. Золотой набор (схема записи)

Кейс = один довод жалобы (в одном решении может быть несколько доводов).

```text
case_id
procurement_id / url
notice_date              # дата извещения → редакция закона
fas_decision_id / url
topic                    # ooz_33 / participants_31 / notice_42 / contract_34
complaint_argument       # текст довода жалобы (запрос режима D, см. §6.1)
doc_fragment             # фрагмент извещения / приложения, к которому относится довод (+ локатор)
outcome                  # upheld / rejected  (довод обоснован / не обоснован)
gold_norms[]             # norm_id в каноне §4.2; до уровня пункта; подпункты → id пункта
relies_on_bylaw          # bool, см. §3.2
doc_paths[]              # локальные пути к извещению и приложениям
gold_notes               # краткий paraphrase для человека; не для строгой метрики
split                    # dev / eval  (подбор порогов vs финальный прогон)
```

### 4.4. Риск данных (главный)

Парсинг решений ФАС и приложений (docx / pdf / xlsx) может съесть больше времени, чем модель. В плане
заложен явный бюджет (см. §9). Если за 2 недели не набирается 20 чистых кейсов — сузить до тем ст. 33 и
ст. 31 или размечать `complaint_argument` / `gold_norms` полуручно из прочитанных решений.

### 4.5. Сбор решений ФАС

**Основной источник — реестр жалоб ЕИС** (zakupki.gov.ru, раздел контроля):

- фильтры: закон (44-ФЗ), период, результат (обоснована / частично / не обоснована), поиск по тексту;
- в карточке — текст жалобы и решение контрольного органа (pdf / docx);
- **номер закупки** → извещение и приложения. Готовая связка «жалоба ↔ решение ↔ документ».

**Дополнительный — база решений ФАС** (br.fas.gov.ru): полнотекстовый поиск по формулировкам
(«или эквивалент», «статьи 33»). Номер извещения извлекается из текста решения регуляркой.

**Массовые XML-выгрузки ЕИС** (жалобы, проверки, извещения) — после MVP; актуальные условия доступа
проверить на старте. Для 25–30 кейсов не нужны.

**Порядок:**

1. **Вручную первые ~10 кейсов** — понять структуру решений: обычно ФАС разбирает каждый довод отдельно
   с выводом «обоснован / не обоснован».
2. **Скрипт:** выгрузка решений по фильтру → регулярки для норм (`ч. 1 ст. 33` → `norm_id` §4.2) и номера извещения →
   скачивание приложений извещения.
3. **Ручная проверка** каждого довода: текст довода, фрагмент документа, вывод ФАС, нормы.
4. Частично обоснованные жалобы разбиваются на доводы — каждый довод со своим `outcome`.

Скачивание — с паузами между запросами и локальным кэшем; сырые файлы не коммитятся.

## 5. Версионирование редакций

**Идеал:** проверять закупку по редакции 44-ФЗ на дату извещения.

**MVP:** извещения с 2025-01-01 + одна **актуальная** редакция 44-ФЗ (`edition_id` фиксируется при
скачивании, см. §13.1). В README: «полное версионирование по `notice_date` — следующая итерация».

После MVP: хранение редакций, `norm_id` стабилен внутри редакции, выбор редакции по `notice_date`;
добавление более старой редакции и кейсов до 2025.

## 6. Архитектура (логическая)

Один линейный пайплайн (без обязательного LangGraph):

```text
Вход: пакет документов  ИЛИ  (complaint_argument + doc_fragment)
    → парсинг и нормализация текста
    → фрагментация извещения / фрагмента (§6.0)
    → кандидаты:
         скан: эвристики по темам (+ опц. LLM)     ← обязателен в режиме скана
         довод: кандидат(ы) из полей пользователя  ← эвристики по пакету не обязательны
    → построение запроса по кандидату (§6.1)
    → retrieval по корпусу 44-ФЗ (BM25 / dense / hybrid)
         индекс = чанки норм; query = текст запроса кандидата (не весь пакет в эмбеддер)
    → LLM: structured output по JSON schema (схема замечания)
         по кандидату; вызовы можно распараллелить (на CPU упрёмся в очередь llama-server)
    → валидаторы:
         schema OK?
         norm_id exists?
         norm_quote in norm_text?
         doc_quote in doc_text?
    → фильтр / verdict (заказчик: violation+uncertain; участник: только violation с опорой)
    → JSON-отчёт: список замечаний (+ логи для eval)
```

Поиск кандидатов в режиме скана обязателен: ТЗ с сотнями позиций не помещается в контекст, особенно на CPU.

### 6.0. Входы пайплайна и нарезка извещения

#### Режим скана (заказчик; участник без своего довода)

1. Парсим загруженные файлы (извещение, ООЗ/ТЗ, проект контракта и т. п.) в плоский текст с локаторами
   (`path`, по возможности page / char_span).
2. **Фрагментируем извещение** — отдельно от чанкинга закона (§4.2). Цель: куски, с которыми можно
   работать эвристикам и (если нужно) LLM, а не уместить весь пакет в окно эмбеддера.
   - Сначала по естественным границам: файл → раздел / заголовок → абзац / пункт перечня.
   - Если фрагмент длиннее порога (ориентир = тот же порядок, что `max_chunk` норм, старт **2000**
     символов; параметр эксперимента) — скользящие окна с overlap внутри раздела.
   - Весь пакет **не** эмбеддится целиком: в dense/BM25 по 44-ФЗ уходит только **query кандидата**;
     чанки извещения — источник `doc_fragment` / `doc_quote`, не документы индекса закона.
3. Эвристики (режим запроса C) бегают по фрагментам и дают кандидатов; не требуется «взять ровно
   10 из 100 чанков» — число кандидатов = число срабатываний (+ лимит сверху для CPU).

#### Режим довода (участник указал гипотезу)

1. Вход: **`complaint_argument`** + **`doc_fragment`** (+ опционально локатор / путь к файлу).
2. Если `len(doc_fragment) ≤` порога фрагмента — один кандидат: документ не режем.
3. Если длиннее — нарезаем `doc_fragment` теми же правилами, что в скане; на каждый кусок (или на
   куски, которые пользователь/эвристика связала с доводом) строим кандидата с **тем же** доводом.
4. Запрос к retrieval (предпочитаемый): текст **довода** (аналог режима D / уточнённый B).
   Допустимо добавить к query короткую цитату из фрагмента; **не** склеивать довод и весь фрагмент
   в один вектор «вместо» довода и не класть извещение в индекс норм.
5. Дальше — как в общем пайплайне: top-k норм → LLM → валидаторы → замечание(я) в отчёте.

Eval retrieval на этапе 1 остаётся на режиме D (довод из решения ФАС); режим довода в продукте —
тот же класс запросов с пользовательским вводом.

### 6.1. Чем является запрос к retrieval

| Режим | Запрос | Где используется |
| --- | --- | --- |
| **A** | Фрагмент документа как есть | Нижняя граница в end-to-end eval |
| **B** | Гипотеза нарушения, сформулированная LLM по фрагменту («указан товарный знак без „или эквивалент“») | Пайплайн, опционально; сравнение в end-to-end eval |
| **C** | Кандидат от эвристики: шаблон `issue_type` + цитата фрагмента | Основной режим пайплайна |
| **D** | Довод жалобы (`complaint_argument`) | Eval retriever (этап 1); в продукте — режим довода (§6.0) |
| **E** | Без retrieval: таблица `issue_type → нормы` | Обязательный baseline |

Логика:

- **Этап 1** — retriever оценивается на режиме D: чистая пара «запрос → нормы» с экспертной разметкой.
- **Этап 2** — в пайплайне кандидаты находит C, опционально уточняет B; в end-to-end eval сравниваются
  A / B / C как способы построить запрос, с ценой B в секундах на CPU.
- **Baseline E** отвечает на вопрос, нужен ли retrieval вообще. Если таблица даёт recall ~95% на известных
  типах — это честный вывод; retrieval тогда оправдан для смежных норм и типов вне таблицы.

### 6.2. Retrieval

Индекс — весь 44-ФЗ. Сравнить и **измерить**:

1. Dense only (эмбеддер из ruMTEB, напр. FRIDA; на CPU)
2. BM25 only
3. Hybrid (RRF или взвешенное слияние)
4. (После MVP) hybrid + rerank

Чанкинг норм (схема корпуса — §4.2):

- **A:** структурный — часть целиком (если влезает) → иначе пункт → иначе окна внутри пункта
- **B:** окна фиксированной длины с overlap по `Edition.full_text`; у каждого окна `norm_ids[]` по пересечению оффсетов

Заголовок статьи (`NormUnit.title`): хранить отдельно; в `Chunk.text` — с префиксом или без — сравнить на
бенче (влияет на BM25, не на валидатор цитат: `norm_quote` проверяется по `NormUnit.text` без префикса).

Метрики — в §7.1.

### 6.3. Генерация: on-prem на CPU

- **Движок:** `llama-server` (llama.cpp), OpenAI-совместимый API. Клиент в коде — обычный
  OpenAI-совместимый, поэтому бэкенд меняется без правок пайплайна (vLLM, внешний API).
- **Основная модель:** T-lite-it-2.1 (GGUF, Q5_K_M или Q6_K): русский, tool-calling, Apache-2.0,
  шаблон Qwen3 (`--jinja`). Q4_K_M — дополнительная точка на графике «качество / скорость»: по карточке
  модели у неё заметная просадка на Ru Arena Hard.
- **Модель для сравнения:** YandexGPT-5-Lite-8B-instruct (GGUF). Нестандартный шаблон диалога, tool-calling
  не заявлен, ограничительная лицензия — поэтому только как вторая точка сравнения.
- **Эталон через API (этап 2, не блокер MVP):** одна крупная модель через внешний API, тот же пайплайн
  и та же схема замечания. Сравнение с T-lite — в первую очередь по **faithfulness** (§7.1): доля
  валидных `norm_id` / `norm_quote` / `doc_quote` / полной двусторонней опоры. Качество против ФАС и
  скорость — вторично (API быстрее и дороже, цифры несопоставимы один в один).
- **Ускорение:** проверить Vulkan-бэкенд на встроенной графике (Radeon 780M) для prefill; решение — по
  замерам `llama-bench`, а не по ожиданиям.
- **Structured output:** JSON schema → грамматика в llama.cpp; модель физически не может вернуть
  невалидный JSON. Схема — Pydantic v2.
- **Промпт:** роль «помощник эксперту», запрет выдумывать нормы, требование цитат, явный отказ при
  нехватке оснований.
- **Контекст:** 3–5 структурных фрагментов нормы вместо десятка окон — prefill на CPU дорогой.

### 6.4. Tool-calling (этап после вертикального среза)

Минимальный инструмент: `get_norm_text(norm_id) -> str`.  
Модель не цитирует норму «по памяти», а запрашивает текст. На MVP сначала подставлять top-k фрагментов в
контекст без tools; tools — когда базовая валидация цитат уже работает. Держать состав инструментов
минимальным.

### 6.5. Почему не LangGraph в MVP

Явные функции + state в dataclass/dict проще читать и отлаживать. Тяжёлые оркестраторы не тащить без
измерения. Если появится реальная ветвистая логика — пересмотреть.

## 7. Eval-харнесс

Каталог `evals/` — первоклассный гражданин репозитория.

### 7.1. Метрики MVP (обязательные)

**Retrieval (режим D, кейсы `upheld`, без `relies_on_bylaw`)**

- recall@5, recall@10 на двух уровнях: **по статье** и **по части / пункту** (разница методов видна на втором);
- доля кейсов, где найдено **всё** множество `gold_norms` (ФАС часто цитирует несколько норм);
- таблица: dense / BM25 / hybrid × чанкинг A/B + baseline E; разбивка по темам.

**Faithfulness (программно)**

- % `norm_id`, существующих в корпусе;
- % `norm_quote`, найденных в тексте нормы;
- % `doc_quote`, найденных в документе;
- % замечаний с полной опорой с двух сторон.

**Качество замечаний против решений ФАС — по режимам (§2.3)**

Для каждого режима — своя задача eval, под которую подходят данные:

*Режим «участник» — классификация доводов.* Вход: `doc_fragment` + `complaint_argument`; выход:
обоснован / не обоснован (+ нормы). Отклонённые жалобы — ровно случаи «участник считал нарушением,
а его нет», поэтому:

- **precision и recall точные** (без оговорок про нижнюю границу), основная метрика — precision;
- confusion matrix по темам;
- доля верно названных норм среди верно распознанных нарушений.

*Режим «заказчик» — скан всего документа.* Вход: извещение + приложения целиком.

- **recall по обоснованным доводам** — основная метрика: нашла ли система нарушение, которое признала ФАС;
- **precision — только нижняя граница:** ФАС рассматривает лишь доводы жалобы, а не весь документ, поэтому
  «лишнее» замечание не обязательно ложное. Часть лишних замечаний проверяется вручную, результат
  указывается отдельно;
- **доля корректных отказов** на кейсах `rejected`: система не выдаёт `violation` на фрагменте, где ФАС
  нарушения не нашла;
- среднее число замечаний на документ — прокси нагрузки на пользователя.

Итоговая таблица в README: две рабочие точки (заказчик / участник) с их метриками на одном наборе кейсов.

**Производительность (on-prem)**

- prefill и генерация, токенов/с (CPU vs Vulkan);
- секунд на кейс, p50 / p95, отдельно retrieval и генерация;
- сравнение квантизаций (Q4 / Q5 / Q6) по качеству и скорости.

### 7.2. Метрики после MVP

- LLM-as-judge только как вспомогательный сигнал с калибровкой на ручном срезе;
- метрики по режимам запроса A / B / C на расширенном наборе.

### 7.3. Принцип

Одна команда (`make eval` / `pytest` + скрипт) должна воспроизводить таблицы из README. Без «цифр из чата».
Ответы LLM кэшируются по hash(prompt, model, params) — иначе полный прогон на CPU занимает часы.

**Выход недели 2:** вертикальный срез пайплайна с воспроизводимыми метриками.

## 10. Критерии успеха MVP

Считаем MVP достигнутым, если одновременно:

1. Есть публичный репозиторий с воспроизводимым `eval` на ≥20 кейсах (или задокументированным меньшим N),
   включая отклонённые жалобы.
2. Есть таблица retrieval по всему 44-ФЗ: минимум 2 метода × 2 чанкинга + baseline E, на двух уровнях детализации.
3. Генерация замечаний проходит через схему; доля полной двусторонней опоры измерена и указана в README.
4. Есть метрики для двух рабочих точек: precision / recall классификации доводов («участник») и recall по
   обоснованным доводам при скане документа («заказчик»).
5. Замерены скорость и задержка on-prem инференса на CPU.
6. В README есть раздел ограничений метрик (в т. ч. про precision как нижнюю границу в режиме «заказчик»)
   и правовой дисклеймер.
7. Нет непроверенных бизнес-цифр.

#### Исследование по п. 1 (2026-09-29)

Главный разрыв редакций для наших статей — не «размазанный 2024–2026», а **порог 1 января 2025** (ФЗ от 08.08.2024 № 318-ФЗ; плюс пакет с № 484-ФЗ по ст. 34).

| Статья | Что менялось в окне ~2024–2026 | Критично для MVP? |
| --- | --- | --- |
| **ст. 33** | ч. 1.1 изложена заново (318-ФЗ); применяется к извещениям с **01.01.2025**. Ядро ч. 1 (товарный знак / «или эквивалент») стабильно с правок 2021/2023 | **да** — ч. 1.1 и связка со ст. 14 |
| **ст. 42** | п. 15 ч. 1 переписан под новый нацрежим (318-ФЗ), с **01.01.2025** | да для темы «извещение» (после MVP) |
| **ст. 14** | крупная реформа нацрежима (318-ФЗ), с **01.01.2025** | косвенно: кейсы на ПП / нацрежим → `relies_on_bylaw` |
| **ст. 34** | расширение ч. 15 (упрощённая форма контракта), ~**01.01.2025** (484-ФЗ) | да для темы контракта (после MVP) |
| **ст. 31** | текст 44-ФЗ для MVP относительно стабилен; доптребования живут в **ПП № 2571** (не в корпусе MVP). Существенные правки ст. 31 ожидаются с **2026** (138-ФЗ) | низкий риск для корпуса закона |
| **ст. 8 (44-ФЗ)** | принципы КС; путаница: в обзорах часто цитируют **ст. 8 закона № 360-ФЗ** (переходные нормы), это **не** ст. 8 44-ФЗ | для gold — уточнять, что имеется в виду |

**Решение для MVP (зафиксировано):**

1. Окно кейсов: извещения, размещённые в ЕИС **с 2025-01-01**.
2. Корпус: **актуальная** редакция 44-ФЗ (включает пакет 318-ФЗ / 484-ФЗ) → `edition_id` = дата вступления в силу / дата редакции с pravo.gov.ru при скачивании (ожидаемо ≥ `2025-01-01`); зафиксировать в `edition.json` вместе с `content_sha256`.
3. Более старая редакция и кейсы с извещением до 01.01.2025 — **после** работающего пайплайна и eval (не блокер MVP).
4. Кейсы, где ФАС опирается в основном на ПП № 1875 / КТРУ — флаг `relies_on_bylaw`.

Ранее рассматривалась альтернатива «только 2024» — отклонена в пользу свежего окна + одна актуальная редакция.
